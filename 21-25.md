## What are Embeddings and How Are They Used in RAG?

**Embeddings** are numerical vector representations of text that capture its **semantic meaning**.

### How embeddings are used in RAG

1. **Document Chunking**

   * Documents are split into smaller chunks.

2. **Create Document Embeddings**

   * Each chunk is converted into a numerical vector using an **embedding model**.

3. **Store in Vector Database**

   * The embeddings are stored in a vector database such as Chroma, FAISS, or Pinecone.

4. **Embed the User Query**

   * The user's query is converted into a vector using the **same embedding model**.

5. **Similarity Search**

   * The query vector is compared with document vectors using measures such as **cosine similarity**.
   * The most semantically similar chunks are retrieved.

6. **Pass Context to LLM**

   * Retrieved chunks are provided to the LLM as context to generate the final answer.

### Example

```text
Document → Chunks → Embeddings → Vector Database
                                      ↑
User Query → Query Embedding → Similarity Search
                                      ↓
                              Relevant Chunks
                                      ↓
                                     LLM
                                      ↓
                                   Answer
```

### Key Point

> **Embeddings convert text into vectors so that RAG can find documents based on semantic meaning rather than only exact keyword matches.**


## Key Considerations When Choosing an Embedding Model

Choosing the right embedding model is important because it directly affects **retrieval quality** in a RAG system.

* **Embedding Quality**

  * Should capture the semantic meaning of queries and documents accurately.

* **Domain Performance**

  * Choose a model that performs well for your domain, such as **technical, legal, medical, or financial** content.

* **Retrieval Performance**

  * Evaluate how well the model retrieves relevant documents using metrics like **Recall@K, Precision@K, and MRR**.

* **Language Support**

  * If your documents contain multiple languages, choose a **multilingual embedding model**.

* **Embedding Dimensions**

  * Higher dimensions can represent more information but may require more **storage and computation**.

* **Latency**

  * Consider how quickly the model can generate embeddings, especially for large document collections or real-time applications.

* **Cost**

  * Consider API pricing or infrastructure costs for generating embeddings.

* **Scalability**

  * The model should handle large numbers of documents and queries efficiently.

* **Domain Adaptation**

  * Specialized or fine-tuned embedding models may perform better for domain-specific data.

* **Compatibility**

  * The query and document embeddings should be generated using the **same compatible embedding model** and configuration.

### Remember:

> **Choose an embedding model based on Quality + Domain + Retrieval Performance + Language + Dimensions + Latency + Cost + Scalability.**

## What is a VectorDB?

A **Vector Database (VectorDB)** is a database designed to **store, index, and search vector embeddings** efficiently.

In RAG, it stores embeddings of document chunks and helps retrieve the chunks that are **most semantically similar** to a user's query.

### How VectorDB is Used in RAG

1. **Split Documents**

   * Documents are divided into smaller chunks.

2. **Create Embeddings**

   * Each chunk is converted into a numerical vector using an embedding model.

3. **Store in VectorDB**

   * The vectors, along with the original text and metadata, are stored in the vector database.

4. **Convert Query to Embedding**

   * The user's query is converted into a vector using the same embedding model.

5. **Similarity Search**

   * VectorDB compares the query vector with stored vectors using similarity measures such as **cosine similarity**.
   * The most relevant chunks are retrieved.

6. **Send Context to LLM**

   * Retrieved chunks are passed to the LLM to generate the final answer.

### RAG Flow

```text id="4j8j8c"
Documents
    ↓
Chunking
    ↓
Embedding Model
    ↓
VectorDB
    ↑
Query → Query Embedding
    ↓
Similarity Search
    ↓
Relevant Chunks
    ↓
LLM
    ↓
Final Answer
```

### Examples of VectorDBs

* **Chroma**
* **FAISS**
* **Pinecone**
* **Qdrant**
* **Milvus**
* **Weaviate**

### Remember:

> **VectorDB = Store + Index + Search embeddings → Retrieve relevant context → LLM generates the answer.**


## Step-by-Step Working of ANN Algorithms in RAG

**ANN (Approximate Nearest Neighbor)** search is used to quickly find the most similar document vectors from a large vector database.

### Step 1: Split documents

* Large documents are divided into smaller **chunks**.

### Step 2: Generate embeddings

* Each chunk is converted into a numerical vector using an **embedding model**.

```text
Document Chunk → Embedding → Vector
```

### Step 3: Build an ANN index

* The vectors are organized into an optimized index.
* Common techniques include **HNSW, IVF, PQ, and ScaNN**.
* The index helps avoid comparing the query with every vector.

### Step 4: Convert the user query into an embedding

* The user's question is converted into a vector using the **same embedding model**.

```text
User Query → Query Embedding → Query Vector
```

### Step 5: Search the ANN index

* The ANN algorithm searches the index for vectors that are close to the query vector.
* It searches a limited set of promising candidates instead of the entire database.

### Step 6: Calculate similarity

* Similarity between the query and candidate vectors is calculated using measures such as **cosine similarity** or **dot product**.

### Step 7: Select Top-K results

* The most similar vectors are selected.

```text
Query
  ↓
ANN Search
  ↓
Candidate Vectors
  ↓
Similarity Scoring
  ↓
Top-K Relevant Chunks
```

### Step 8: Send results to the LLM

* The retrieved chunks are provided as context to the LLM.
* The LLM uses this context to generate the final answer.

### Complete RAG Flow

```text
Documents
    ↓
Chunking
    ↓
Embeddings
    ↓
ANN Index
    ↓
Vector Database
          ↑
          │
User Query → Query Embedding
          ↓
      ANN Search
          ↓
      Top-K Chunks
          ↓
         LLM
          ↓
     Final Answer
```

### Why ANN is fast

**Exact search:**

> Query → Compare with every vector → Find nearest vectors

**ANN search:**

> Query → Navigate/search optimized index → Check promising candidates → Find nearest vectors

Therefore, ANN provides **fast and scalable retrieval** for large RAG knowledge bases, while accepting a small possibility of missing the mathematically exact nearest neighbor.

### Remember

> **Chunk → Embed → Index → Query → ANN Search → Similarity → Top-K → LLM**
