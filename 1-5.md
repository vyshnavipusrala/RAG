# Retrieval-Augmented Generation (RAG)

## 1. Why is RAG required when LLMs are already powerful?

Large Language Models (LLMs) are powerful, but they have limitations when working with **private, frequently changing, or domain-specific information**.

### Key reasons for using RAG

* **Access to private/company data**
  LLMs are not automatically aware of an organization's internal documents, databases, policies, or knowledge bases.

* **Knowledge can become outdated**
  An LLM's knowledge may not contain the latest information. RAG allows the system to retrieve up-to-date information from an external knowledge source.

* **Reduces the need for retraining**
  When company data changes, we can update the knowledge base instead of retraining the entire LLM.

* **Reduces hallucinations**
  By providing relevant retrieved context to the LLM, RAG can help ground the generated response in available information.

* **Source attribution**
  RAG systems can be designed to return the documents or sources used to generate an answer, making responses easier to verify.

### Simple Example

Imagine a company has 10,000 internal documents.

Instead of retraining an LLM whenever one document changes:

```text
User Query
    ↓
Retrieve relevant company documents
    ↓
Add retrieved information to the prompt
    ↓
LLM generates the answer
```

This is the basic idea behind **Retrieval-Augmented Generation**.

# 2. Is RAG still relevant in the era of Long-Context LLMs?

**Yes. RAG is still important even when LLMs support very large context windows.**

Long-context LLMs can process large amounts of information, but simply providing more context does not always mean better results.

### Limitations of Long-Context LLMs

#### 1. Lost in the Middle

When a very large amount of information is provided, the model may not pay equal attention to every part of the context.

Important information located in the middle of a large context can be harder for the model to use effectively.

#### 2. Higher API Costs

Processing a large context means processing more tokens.

More tokens can lead to:

* Higher API costs
* Higher computational requirements

#### 3. Increased Latency

Larger prompts generally require more processing.

Therefore:

```text
More context
     ↓
More tokens to process
     ↓
Higher processing time
     ↓
Higher latency
```

### Why RAG still helps

Instead of sending an entire knowledge base to the LLM:

```text
10,000 documents
       ↓
    Retrieval
       ↓
Top relevant documents
       ↓
      LLM
       ↓
    Answer
```

RAG focuses the model's context on information that is more relevant to the user's query.

# 3. Challenges of RAG Systems

RAG problems can generally be divided into two major categories:

```text
                 RAG Challenges
                      │
             ┌────────┴────────┐
             ↓                 ↓
        Retrieval           Generation
         Problems            Problems
```

## A. Retrieval Problems

### Wrong Chunks

The retriever may return documents or chunks that are not relevant to the user's question.

### Poor Chunking

If documents are split incorrectly, important information can be separated across chunks.

Poor chunking can result in incomplete or irrelevant retrieval.

### Bad Embeddings

If the embedding model does not represent the meaning of the query and documents effectively, similarity search may return poor results.

### Query Ambiguity

A vague or unclear user query can make it difficult for the retriever to understand what information should be retrieved.

### Stale Documents

If the knowledge base contains outdated information, the retrieved context may also be outdated.

---

## B. Generation Problems

### Hallucination

The LLM may generate information that is not supported by the retrieved context.

### Poor Reasoning

Even when the correct information is retrieved, the LLM may incorrectly interpret or combine the information.

### Context Overload

Too much retrieved information can make it harder for the model to identify the most relevant content.

### Unsupported Answers

The generated answer may contain claims that cannot be supported by the retrieved documents.

# 4. Effective Strategies to Reduce Latency in RAG Systems

Latency can be reduced by optimizing both the **retrieval pipeline** and the **generation process**.

### 1. Reduce the Number of Retrieved Documents

Retrieve only the documents or chunks that are necessary.

For example:

```text
Instead of retrieving 20 chunks
            ↓
Retrieve the top 3–5 relevant chunks
```

This reduces the amount of context sent to the LLM.

### 2. Use a Fast Vector Database

Choose an efficient vector database and configure the indexing and search parameters appropriately.

Examples include:

* Chroma
* FAISS
* Pinecone
* Weaviate
* Milvus

### 3. Limit Unnecessary Reranking

Reranking can improve retrieval quality, but it introduces additional computation.

Use reranking selectively when it provides enough quality improvement to justify the added latency.

### 4. Parallelize Independent Operations

Operations that do not depend on each other can be executed in parallel.

For example:

```text
             User Query
                 │
       ┌─────────┴─────────┐
       ↓                   ↓
   Vector Search       Keyword Search
       │                   │
       └─────────┬─────────┘
                 ↓
              Combine
```

### 5. Reduce LLM Calls

Multiple LLM calls can significantly increase latency.

Where possible, simplify the pipeline and avoid unnecessary query rewriting, summarization, or validation calls.

### 6. Use Faster or Smaller Models

Smaller models can often provide significantly lower latency for tasks that do not require a highly capable model.

### 7. Reduce Context Size

Send only the most relevant information to the LLM instead of the entire retrieved dataset.

### 8. Use Caching

Caching can avoid repeating expensive operations.

Common examples:

* **Embedding cache** — avoid generating embeddings repeatedly for the same content.
* **Retrieval cache** — reuse retrieval results for repeated queries.
* **Response cache** — reuse responses for frequently asked questions when appropriate.

# 5. What do R, A, and G mean in RAG?

RAG stands for:

> **Retrieval-Augmented Generation**

It consists of three main stages:

```text
R → Retrieval
A → Augmentation
G → Generation
```

---

## R — Retrieval

**Retrieval** is the process of searching for and fetching the most relevant information from external knowledge sources based on the user's query.

### Example

```text
User:
"What is our company's leave policy?"

        ↓

Retriever

        ↓

Search knowledge base

        ↓

Relevant policy documents
```

The retriever may use techniques such as:

* Vector similarity search
* Keyword search
* Hybrid search
* Metadata filtering
* Reranking

---

## A — Augmentation

**Augmentation** means adding the retrieved information to the prompt along with the user's query and instructions.

Conceptually:

```text
System Instructions
        +
User Query
        +
Retrieved Context
        ↓
     Prompt
```

Example:

```text
Context:
Employees are entitled to 20 days of annual leave...

Question:
How many annual leave days are employees entitled to?

        ↓

Augmented Prompt
```

The retrieved context gives the LLM additional information to use when answering.

---

## G — Generation

**Generation** is the process where the LLM uses the augmented prompt to generate the final response.

```text
Retrieved Context
       +
User Query
       +
Instructions
       ↓
      LLM
       ↓
Final Answer
```

The goal is to generate an answer that is:

* Relevant
* Grounded in the retrieved information
* Useful to the user
* Consistent with the available context

---

# Overall RAG Pipeline

The complete RAG workflow can be summarized as:

```text
                    USER QUERY
                        │
                        ↓
                 Query Processing
                        │
                        ↓
                   RETRIEVAL
                        │
            ┌───────────┴───────────┐
            ↓                       ↓
      Vector Search            Keyword Search
            │                       │
            └───────────┬───────────┘
                        ↓
                  Relevant Chunks
                        │
                        ↓
                    AUGMENTATION
                        │
              Query + Context
                        │
                        ↓
                   GENERATION
                        │
                        ↓
                      LLM
                        │
                        ↓
                  FINAL ANSWER
```

## One-Line Interview Definition

**RAG is a technique that retrieves relevant information from an external knowledge source and provides it as context to an LLM so that the model can generate more relevant and grounded responses without requiring the model to be retrained whenever the external data changes.**
