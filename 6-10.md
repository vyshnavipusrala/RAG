# Why is Re-ranking important?

When fetching the top-k chunks, some of them may be irrelevant. Passing these chunks directly to the LLM can hurt the quality of the generated response.

A re-ranker uses a **cross-encoder** technique to measure the relevance of each chunk to the user query and re-rank the chunks. This reduces noise and helps the LLM generate more accurate responses.

# Purpose of overlap during chunking in a RAG pipeline

* Preserves context across chunk boundaries.
* Prevents important information from being split between chunks.
* Improves retrieval when the relevant information spans two chunks.
* Helps the LLM understand the complete meaning of retrieved content.

# Role of cosine similarity in relevant chunk retrieval

Cosine similarity measures how similar the **query embedding** is to the **embeddings of chunks** in the vector database.

It measures the angle between the embedding vectors and produces a similarity score. Chunks with higher similarity scores are considered better matches for the query.

# Complete RAG Pipeline

A RAG pipeline consists of two main phases:

1. **Indexing Phase** — preparing and storing the knowledge.
2. **Query Phase** — retrieving relevant information and generating a response.

## 1. Indexing Phase

```text
Documents
    ↓
Document Loading
    ↓
Document Parsing
    ↓
Chunking
    ↓
Embedding Generation
    ↓
Vector Database
```

### Document Loading

Documents are loaded from external knowledge sources such as:

* PDFs
* Word documents
* Text files
* Websites
* Databases

### Document Parsing

The content is extracted from the documents so that it can be processed by the RAG system.

### Chunking

Large documents are divided into smaller chunks so that relevant information can be retrieved efficiently.

```text
Large Document
      ↓
 ┌────┬────┬────┬────┐
 ↓    ↓    ↓    ↓
 C1   C2   C3   C4
```

### Embedding Generation

Each chunk is converted into a numerical vector using an embedding model.

```text
Text Chunk
    ↓
Embedding Model
    ↓
Vector
```

### Vector Database

The generated embeddings, along with the corresponding chunks and metadata, are stored in a vector database.

---

# 2. Query Phase

```text
User Query
    ↓
Query Embedding
    ↓
Similarity Search
    ↓
Retrieve Top-K Chunks
    ↓
Re-ranking
    ↓
Relevant Context
    ↓
Prompt Augmentation
    ↓
LLM
    ↓
Final Answer
```

### Query Embedding

The user's query is converted into an embedding using an embedding model.

### Retrieval

The query embedding is compared with the stored document embeddings to retrieve the most relevant chunks.

Retrieval can use:

* Vector search
* Keyword search
* Hybrid search
* Metadata filtering

### Re-ranking

The initially retrieved chunks are passed through a re-ranker to improve their ordering based on their relevance to the query.

### Prompt Augmentation

The retrieved context is combined with the user's query and instructions to create the final prompt.

```text
Instructions
     +
User Query
     +
Retrieved Context
     ↓
Augmented Prompt
```

### Generation

The LLM processes the augmented prompt and generates the final response.
